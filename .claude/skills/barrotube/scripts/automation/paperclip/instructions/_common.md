## 공통 규약 — BarroTube 자동화 (2026-10 체제)

**채널**: 바로경제 — 한국어 경제 쇼츠 유튜브 채널. 생산은 결정론 파이프라인(`lib/auto-pipeline.sh`)이 한다.
에이전트는 그 위에서 판단이 필요한 곳만 맡는다. 운영자는 텔레그램과 이 페이퍼클립 화면으로만 본다.

**정본 위치** (스킬 루트 `/Users/beye/workspace/BarroSkills/.claude/skills/barrotube`, 이하 `$BT`)
- 편성·슬롯: `$BT/config/routines.json` · 페이퍼클립 구성: `$BT/config/paperclip/company.json`
- KPI 정의: `$BT/config/growth.json` · 오늘 KPI: `$BT/workspace/growth/kpi/<날짜>.md`
- 장애 설계서: `$BT/workspace/growth/incidents/<id>.md` · 장애·처리 기록: `$BT/workspace/growth/incidents.jsonl`
- 토큰 상태: `$BT/workspace/ops/token-state.json` · 회차 마커: `$BT/workspace/ops/runs/<날짜>/`
- 작업 폴더: 페이퍼클립은 이슈가 속한 프로젝트의 폴더에서 깨울 수 있다. 그러니 파일은 늘 `$BT/…` 절대 경로로 읽고 쓴다.

**언제 일하는가** — 이 세 가지로 깼을 때만 일한다.
1. 페이퍼클립 루틴(cron)이 만든 이슈  2. 이 문서가 허락한 위임 경로로 만들어진·다시 맡겨진 이슈  3. (CEO) 토큰 거버너가 연 `[막힘 점검]` 이슈
타이머로 깨지 않는다. 할 일이 없으면 「할 일 없음」 한 줄 남기고 끝낸다.

**위임은 네 경로뿐이다** — 그 밖의 이슈 생성·배정·루틴/에이전트/예산 변경은 하지 않는다.
- SRE → Code Reviewer : 패치 리뷰 요청 (장애 1건당 1회, 재리뷰 1회까지)
- SRE → Producer : `action: resume` 재개 요청 (장애 1건당 최대 2회)
- CEO → SRE : 채택한 성장 제안의 구현 (주 1건 이하)
- CEO → SRE·Code Reviewer·CMO : 막힘 점검에서 멈춘 이슈를 다시 맡기기 (`triage.js` 로만, 같은 이슈 하루 2회까지)
`🧭 CEO 막힘 점검` 댓글로 다시 맡겨진 이슈는 그 지시부터 읽고 이어서 한다. 지시가 틀렸으면(이미 끝났음·사람 몫) 이유를 댓글로 남기고 그에 맞게 닫거나 board 로 넘긴다.

**토큰 규율** — 구독 한도는 운영자 본인의 대화 세션과 같이 쓴다.
- 같은 파일을 두 번 통째로 읽지 않는다. 큰 로그는 `tail`/`grep` 으로 필요한 줄만.
- 기다리려고 `sleep`·폴링하지 않는다. 결과를 기다려야 하면 이슈를 blocked 로 두고 끝낸다 — 댓글이 오면 다시 깬다.
- 한 실행에서 끝낼 수 없는 일은 다음 깸으로 넘긴다. 무리해서 턴을 늘리지 않는다.
- `$BT/workspace/ops/token-state.json` 의 내 공급자 상태가 RED 면 필수 일만 하고 나머지는 「한도로 보류」라고 남긴다.

**마무리 규약** — 실행마다 반드시:
1. 이슈에 댓글 1개 (무엇을 봤고, 무엇을 했고, 다음은 무엇인지 — 5줄 안팎, 근거 경로 포함)
2. 상태 변경: 끝났으면 `done`, 남의 결과를 기다리면 `blocked`, 사람이 필요하면 `blocked` + 텔레그램.
   `blocked` 는 막고 있는 것을 같이 넣어야 받아들여진다 — 기다리는 이슈면 `blockedByIssueIds`,
   아니면 `unblockDescriptor: {"owner": "board", "action": "<사람이 할 일>"}`.
   (`node $BT/scripts/automation/paperclip/tg.js "<한 줄>"` — 인자 하나, HTML 이스케이프는 도구가 한다)
댓글 없이 끝내면 페이퍼클립이 같은 일로 다시 깨운다 — 토큰 낭비다.

**금지** — 비밀값(.env, 토큰, OAuth) 읽기·출력, `git push`·`git reset --hard`·`rm -rf`, 발행 상태(공개/비공개) 직접 변경,
launchd·페이퍼클립 설정 변경, 운영 트리(`$BT`) 파일 직접 수정(SRE 의 `apply` 스크립트 경로만 예외).

## 공통 구독 한도와 자동 모델 전환 (2026-10-26)

이 절은 이전의 고정 Claude/Codex 배정, 반반 사용 목표, 15% 예비분, P0·CEO·PM 한도 예외보다 우선한다. 프로젝트·직무·파일 소유권·제품 검증·사용자 승인 규칙은 그대로 적용한다.

- 전 회사의 Claude/Codex 구독 소비를 함께 계산한다. 주간 잔여분 최소 30% 보존이 목표이며 사용 70% 이상이면 새 실행을 허용하지 않는다. 긴급 작업·총괄·검수도 예외가 아니다.
- 중앙 제어기는 15분 이내의 확인된 주간 창, 진행 중 소비 예약, 다음 모델의 예상 소비, 안전 여유분, 확인된 모델별 한도를 반영해 다음 실행을 선택한다. 낮은 모델·다른 공급자도 같은 판정을 통과해야 한다. 로컬 status/check 성공만으로 중앙 실행 승인이나 예약을 대신하지 않는다.
- 사용량·주간 창·계정·연결이 불명확하거나 오래되면 대기한다. 이전 green 표시, 크레딧 잔액, 세션 한도, 임의의 토큰→주간 % 환산으로 주간 여유를 만들지 않는다. 소비 추정은 측정된 구독 청구량이 아니라 운영상 추정임을 구분한다.
- 실제 선택된 공급자는 해당 실행의 `PAPERCLIP_ACTIVE_PROVIDER`와 실제 run의 adapter/provider/model 기록으로 확인한다. `anthropic`/`claude`는 Claude, `openai`/`codex`는 Codex 계열이다. 이름·직함·이전 모델표·이전 세션을 실제 계열로 추측하지 않는다. UUID와 역할·프로젝트 범위는 전환 후에도 유지한다.
- 후보 SHA/파일 범위마다 실제 작성 run, 공급자, 모델, 변경 범위, 검증 결과를 남긴다. QA는 해당 후보를 작성하지 않은 사람 역할이면서 실제 작성 공급자와 반대 계열이어야 한다. 공급자가 바뀌면 QA 배정을 다시 확인하며 같은 공급자의 다른 모델로 교차 검수를 대신하지 않는다. 혼합 작성은 범위별 독립 검수 증거가 갖춰질 때까지 완료 처리하지 않는다.
- 반대 계열 QA나 안전한 대체 연결이 없으면 상태를 `blocked`/검수 대기로 남기고 원인·담당자·다음 확인 조건을 기록한다. 구현 완료를 검수 완료로 표시하지 않는다.
- 실행 중 작업, 체크아웃과 미커밋 변경을 보존한다. 모델 전환은 중앙 제어기가 다음 안전한 실행 경계에서 처리한다. 작업자가 임의로 어댑터·한도·예약을 변경하거나 다른 CLI로 한도를 우회하지 않는다.
- 기존 구독 연결만 자동 사용한다. `responsible_user`의 논리적 method 필드만으로 인증 방식을 단정하지 말고 실제 해결된 연결의 method를 따른다. 유료 API 키로 자동 전환하거나 계정을 임의 교체하지 않는다.
- 중앙 상태 `/Users/beye/BarroTubeData/workspace/ops/quota-switch-state.json`의 `enabled: true`에서는 기존 개별 guard가 pause/resume 설정을 경쟁해서 쓰지 않는다. 사용자가 멈춘 에이전트·휴면 조직을 자동 재개하지 않는다.
- 이미 진행 중인 실행이나 사용자가 별도로 사용하는 구독 소비는 남은 잔액을 바꿀 수 있다. 30%는 신규 실행 승인 정책이며 공급자 측 절대 보장을 주장하지 않는다. 실제 잔액·관측 시각·대기 사유를 있는 그대로 보고한다.

## 막힘 규칙 (바로조 막힘 지휘, 2026-10-28)

이 절은 이 문서의 다른 `blocked`·`in_review`·검수 대기 규칙보다 우선한다. 직무·검증·승인 규칙 자체는 그대로다.

1. 한도 대기는 상태를 바꾸지 않는다. 실행이 `Claude usage limit reached …`·`You've hit your usage limit …`·`PAPERCLIP_RESERVE_GUARD`·exit 20/78 로 멈추면 이슈를 그대로 두고 끝낸다 — Paperclip 이 재시도를 예약한다. `blocked` 로 바꾸지 않는다.
2. `blocked` 는 다른 이슈가 끝나야 할 때만 쓴다 — `blockedByIssueIds` 에 실제 선행 이슈를 건다. 계획 단계에서 이슈를 `blocked` 로 만들지 않는다(`todo` 로 만들고 실제 선행만 건다).
3. 사람 판단이 필요해 보이면 human_only 카드나 `in_review` 대기 대신 회사 CEO 에게 넘긴다(댓글로 CEO 를 지목하고 결정할 질문을 적는다). 사람에게만 남기는 일: 결제·계약·법무, 로그인·인증·실물 기기, 되돌릴 수 없는 외부 공개·삭제.
4. 환경·한도·측정이 원인인 장애는 `in_review` 로 기다리지 않는다. 회복이 확인되면 근거를 남기고 `done`.
5. 루틴 점검·보고 이슈는 끝나면 반드시 `done`. 남은 문제는 별도 이슈로 만든다. 점검 이슈 자체를 `blocked`·`in_review` 로 두지 않는다.
6. 「[바로조 막힘 지휘]」 결정 요청 이슈는 다른 일보다 먼저 처리한다.
7. (CEO·총괄) 결정 요청의 뿌리 이슈마다 지금 결정한다(결정·진행 / 재배정 / 범위 쪼개기·가짜 선행 해제 / 완료·취소 / 사람 필요). 보드 권한이 필요하면 요청 이슈 댓글에 한 줄씩 `바로조 요청: restore <이슈>` · `unblock <이슈>` · `close-card <이슈>` · `retry-now <이슈>` · `human <이슈> <사람이 할 일>` 로 적는다. 끝나면 처리표를 남기고 요청 이슈를 `done` 으로 닫는다.
